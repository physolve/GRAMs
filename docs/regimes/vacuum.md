## 1. Назначение

Вакуумирование газового тракта перед экспериментом по методу Сивертса: стравливание избыточного давления в атмосферу (К118), подключение баллонов блока C и второго тракта под откачку. Перенос из GramQt (`SequencerThread` + `testSeq/vacuum_cond.csv`, 56 шагов) на Qt 6.11 TaskTree.

6б. **12.2 «Переход на турбомолекулярный насос»** — гейт (ДВ301 ≤ `turboSwitchPressurePa`, удержание `turboSwitchHoldSec`, ДВ302 валиден) → закрыть К176 → подтвердить readback → открыть К179 → турбо-откачка с контролем ДВ302 и откатом по `turboReturnPressurePa`. `VacuumTaskTree.cpp:buildPumpDownProcedure` / `connectTurboPump`, REQ-077…084. **Выбора в интерфейсе нет** — этап обязателен; рецепт пропускает его сам, только если нет ДВ302 или выключен форвакуум (`setVacuumTurboTract` остался сервисным швом для отладки без турбонасоса).

6в. **11.7б «Общая откачка»** — К171 (`S4`) и К173 (`R4`) открываются **до** форвакуумного тракта, затем К151 (`R3`) и применимые клапаны блока C по флагам `skipRK*`, затем магистраль К178 (`AR5`). После этого — `PumpDownProcedure` целиком: её шаги 1–3 и есть требуемый REQ-056 гейт «ДВ301 ≤ порога с удержанием, и только потом К179». Фаза откачки после перехода идёт `testEvacTimeSec` (REQ-057). По завершении закрывается всё, включая активный насосный клапан (REQ-058). `VacuumTaskTree.cpp:buildGeneralPumping:1346`, узел `VacuumNode::GeneralPumping`.

6г. **11.8 «Проверка герметичности»** — открывается только контрольный участок (`vacuumTract.leakTest` = К171, К173), снимаются начальные показания, выдерживается `leakTestDurationSec`, прирост сравнивается с `dP_leak_max` **поканально**. Превышение хотя бы по одному каналу — `LEAK_DETECTED`, и в режиме «Вакуум» это **предупреждение**: режим продолжается (REQ-062). Недостоверное показание на любом конце выдержки означает «канал не проверен», а не «герметичен». `VacuumTaskTree.cpp:buildLeakTest:1409`, узел `VacuumNode::LeakTest`.

6д. **11.9–11.11 «Подготовка, финальная откачка камеры, закрытие»** — открывается набор `vacuumTract.finalPumping` (К173, К151, К171, К178), затем откачка на одном насосе: подготовка и откачка идут одной группой, потому что закрыть насос между ними значило бы сорвать набранный вакуум. Датчик выбирается по области (REQ-067/069): `targetVacuumPa ≥ turboSwitchPressurePa` — форвакуумная область, контроль по ДВ301, переход на К179 не выполняется; ниже порога — турбо-область, полная `PumpDownProcedure` и контроль по ДВ302. Закрытие идёт обратным обходом, каждый клапан отдельным вызовом шва, то есть отдельной строкой журнала (REQ-070/071). `VacuumTaskTree.cpp:buildFinalPumping:1512`, узлы `FinalPrep` / `FinalPumping` / `FinalClose`.

**Наборы клапанов этапов 11.7б/11.8/11.9–11.10 живут в конфигурации, а не в коде** (REQ-055): `profile/GRAMsPfp.json → vacuumTract`. Пустой набор — не ошибка, а «этап не выполняем»: он даёт `Skipped` с текстом причины через шов `onStageSkipped`. Тихо пропущенный этап читается оператором как выполненный, и для проверки герметичности это худший из возможных исходов.

7. **Непрерывная откачка (опция, финал)** — после успешного завершения **всех** повторов рабочий тракт собирается заново от объёмов к насосу и **остаётся открытым на турбонасосе**: `R3` (К151, камера F + линия E) → `AR5` (К178, бочка; эталонный резервуар B сидит на магистрали и своего клапана не имеет) → закрыть `AR6` (К176) с подтверждением readback → открыть `SL2` (К179). Автоматического закрытия нет. `VacuumTaskTree.cpp:continuousPumpingTail`, узел `VacuumNode::ContinuousPumping`. Включается тумблером «непрерывная откачка» → `RegimeTaskTree::setVacuumContinuousPumping()`, **применяется и во время идущего режима** (шов `VacuumTreeContext::continuousPumpingLive`, слот `VacuumRegimeWorker::onContinuousPumpingChanged`). Не открываются: `AR4` (К118, атмосфера), баллоны C1–C3 и `SL1` (К192).

**Settle-пауза** (`perActionPauseMs` = 3 с) вставляется после каждого дискретного действия рецепта — `VacuumTaskTree.cpp:settlePause`. Значение зафиксировано в коде (тесты ставят 0); настройки в UI нет.

## 4. Поведение при ошибке, отмене и паузе

- **Инвариант 1 (триплет К118 атомарен)**: закрытие `AR4` гарантировано при любом исходе, включая cancel посреди выдержки — `onGroupDone` с `CallDoneFlag::Always` (`VacuumTaskTree.cpp:135`); Storage-флаг `k118Open` подавляет лишнее закрытие после пропуска стражем. Тесты: `CancelDuringPhase1ReliefClosesK118`, `CancelDuringS3TripletClosesInsideOut`.
- **Отмена (фикс краша stop, Day7)**: два независимых источника краша устранены. (1) done-хендлер внешнего дерева при `DoneWith::Cancel` вызывает `worker.cancelTree()` **отложенно** (`QMetaObject::invokeMethod(…, Qt::QueuedConnection)`) — синхронная отмена внутреннего дерева из чужого хендлера продвигала замороженный `QBarrier` («Nested execution of handlers»). (2) `cancelTree()` **отсоединяет** `inner.done → emit done()` перед `cancel()` (`RegimeWorkers.cpp:VacuumRegimeWorker::cancelTree`): иначе отменяемое внутреннее дерево реэмитило `done()` в уже завершённый `QTaskInterface` внешнего `QCustomTask` → краш. Клапаны закрывают done-хендлеры рецепта во время `cancel()`; `endAction`/monitor — прямо в `cancelTree()`. `stop()` дополнительно снимает паузу перед `cancel()`. Все открытые клапаны (включая `AR6`/`AR5`/`R3`) закрываются изнутри-наружу. Тест: `CancelDuringForevacHoldClosesPump`.
- **Заблокированное открытие** (`setValveFromAction → false`): `StopWithError` — остаток повтора пропускается, done-хендлеры закрывают открытое, повтор помечается ошибкой, следующие повторы выполняются (см. неоднозначность №3). Тест: `BlockedSecondTractValveClosesAlreadyOpened`.
- **Пауза**: `PauseBus` → `PausableTicker` замораживает выдержку **с открытым клапаном** (легаси-подобно; см. неоднозначность №4). Тест: `PauseFreezesDwellAndResumeCompletes`.
- **Security-watcher** (`checkValvePressure` во время выдержек): не подключён в Ф1–Ф3, отложен до Ф4 (см. неоднозначность №7).

## 6. Физический смысл

Первый шаг эксперимента по методу Сивертса: сброс избыточного давления и подготовка всех калиброванных объёмов к откачке. Без полного вакуумирования измерение поглощённого H₂ неточно из-за остаточного газа.

## 7а. Бюджет времени прогона — согласованная дивергенция от ТЗ v5

**Расхождение с REQ-032, REQ-033, REQ-068, REQ-069. Согласовано; подлежит
внесению в следующую редакцию ТЗ.**

ТЗ делает `EvacTime` приоритетным условием финальной откачки: откачка идёт до
его истечения даже при достигнутом давлении (REQ-032/068), а при недостигнутом
продлевается до `maxAdditionalEvacTime` (REQ-033/069).

В GRAMs время работает иначе — как **жёсткий потолок сверху**:

| | ТЗ v5 | GRAMs |
|---|---|---|
| Источник времени | `EvacTime`, параметр этапа | `T_total` = время строки RunTable (`max_time`, секунды) |
| Что ограничивает | длительность финальной откачки | **весь прогон режима, от старта Ф1** |
| Достигнутая цель раньше срока | откачка продолжается | завершение с причиной «цель достигнута» |
| Цель не достигнута к сроку | продление до `maxAdditionalEvacTime` | **продления нет**, завершение с причиной «бюджет исчерпан» |
| `maxAdditionalEvacTime` | параметр конфигурации | **отменён**, не реализован |

Как это работает:

- `T_total` берётся из строки RunTable. Поле — `max_time`, **единицы — секунды**
  (`src/runtable/prototablemodel.cpp:207-213`, диапазон 1…86399; в интерфейсе
  вводится как ЧЧ:ММ:СС, `src/runtable/RunTable.qml:122-146`).
- `elapsed` считается от старта Ф1 и включает сброс К118, обработку C1/C2/C3,
  все форвакуумные этапы, общую откачку и проверку герметичности.
- Счётчик обнуляется на входе в Ф1 **каждого повтора**: `max_time` в модели —
  время одного повтора, полное время строки = `(условие + max_time) * repeatCount`
  (`RegimeManager::updateVisibleRegimes`).
- На входе в 11.10 `remaining = T_total − elapsed`, и откачка идёт только
  оставшееся время, а не полный `EvacTime`.
- `remaining ≤ 0` — финальная откачка не запускается вовсе: цель проверяется по
  нужному датчику, причина завершения пишется явно, выполняется закрытие 11.11.
- Любое ожидание внутри режима обрезается остатком, включая `testEvacTime`
  общей откачки и `leakTestDurationSec` проверки герметичности.
- Исчерпанный бюджет завершает прогон **штатно**, а не аварией: «достигнут
  targetVAC», «исчерпан бюджет», «остановлено оператором» и «авария» — четыре
  разных исхода, и они обязаны различаться в журнале и в интерфейсе.

Почему так: оператор планирует эксперимент по строкам RunTable. Строка, которая
может идти дольше объявленного, ломает весь план прогона, а не только себя.

Ограничение реализации: счётчик ведётся в **тиках** рецепта (тик = секунда в
бою, миллисекунда в тестах), а не по часам — иначе тесты получили бы бюджет в
тысячу раз меньше заявленного. `PausableTicker` всегда отрабатывает минимум один
тик, поэтому обнаружение исчерпания стоит до одной секунды. На секундном тике
боевого режима это шум, а не отклонение.

Единицы ДВ301/ДВ302: Торр→Па ×133.322.
9. **dP/dt-проверка (Day7/Day8)** — «мёртвая зона» `pumpCheckDelaySec=30 с` перед **первым** окном (точка `p0` берётся по её истечении, поэтому падение за время выхода насоса на режим в окно не засчитывается), затем окно `pumpCheckWindowSec=5 с` с порогом `pumpMinDropPa=0.25 Па`. На перепроверку после «Продолжить» задержка не накладывается — насос уже работает. Без датчика/без OperatorBus → безопасный отказ. Пороги — ориентиры, уточняются на стенде.
   **Область применимости (2026-09-07):** окно открывается только пока ДВ301 **выше** цели этапа (`PumpRateWatchdog::targetPa` = `targetVacPa`). Если тракт уже на цели или ниже (цель 50 Па, в тракте 30 Па), откачивать нечего: dP/dt по физике близка к нулю, и вердикт «скорость мала» был бы ложным отказом. При достоверном показании ≤ цели задача сразу успешна — без «мёртвой зоны», без окна и без диалога оператора; цель, достигнутая посреди окна, тоже засчитывается как «откачка идёт». Недостоверное показание (мёртвый датчик, отдающий 0) проверку **не** снимает — иначе отказ датчика маскировал бы отказ насоса. То же правило по построению получают все последующие режимы, использующие `PumpRateWatchdog`.
10. **Непрерывная откачка (Day8, переработана 2026-09-07)** — этап `continuousPumpingTail` выполняется **вне** тела `For`, один раз после последнего повтора: иначе повтор N+1 стартовал бы со сброса К118 в атмосферу при открытом насосном клапане. Пропускается при отмене (Стоп) и при `repeatsError > 0` — тракт открывается только после штатного прогона. Открытым остаётся **рабочий** тракт на **турбонасосе**: К151 (камера F + линия E), К178 (бочка; эталон B на магистрали), К179; К176 при этом закрыт. Баллоны C1–C3 и К192 больше не открываются — качать весь объём установки незачем, а К118 (атмосфера) сорвал бы вакуум. Турбоклапан здесь проходит ту же проверку REQ-082, что и переход 12.2 (`connectTurboPump(requireConfirm=true)`): без подтверждённого закрытия К176 он не откроется, и хвост завершится ошибкой. Закрытие тракта после этого — задача оператора; альтернатива (таймер авто-закрытия) не реализована.
    **Живое редактирование:** значение тумблера читается в момент выполнения хвоста (`VacuumTreeContext::continuousPumpingLive`), а не берётся снимком на «Старт». Хвост выполняется в самом конце прогона, который длится десятки минут, — решение оператора, принятое уже во время режима, обязано до него дойти. Без шва (тесты, внешние вызовы) используется поле `continuousPumping`.

12. **Прогресс турбо-этапа (2026-09-07)** — до переключения полоса показывает набор гейта (`turboHeldSec / turboSwitchHoldSec`), после переключения — время турбо-откачки (`turboElapsedSec / turboTimeoutSec`). Критерий завершения турбо-откачки остаётся **временем**: «целевого турбо-вакуума» в ТЗ для 12.2 нет (targetVAC относится к финальной откачке 11.9–11.11), а порог возврата 150 Па сторожит откат, а не завершение. Монитор отдаёт готовые `turboStage` / `turboProgressSec` / `turboProgressMaxSec`, чтобы QML не разбирал `VacuumNode`. Без второй стадии полоса замирала бы на нуле сразу после перехода, и идущая откачка была бы неотличима от зависшего режима.
11. **Жёсткие длительности (Day8)** — 3 с на шаг и 10 с на сброс К118 зафиксированы в `VacuumTreeContext`; настройка из UI удалена вместе с per-step таблицей. Компромисс: гибкость отладки обменяна на предсказуемость прогона; при необходимости настройка возвращается одним Q_INVOKABLE.
