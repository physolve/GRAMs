# `src/actions/` — автоматические режимы

Папка содержит два несовместимых подхода к исполнению действий. Раньше они лежали
вперемешку, и новый режим легко было написать «как соседний файл», выбрав неверный
образец. Теперь подход виден из пути.

## Раскладка

| Папка | Что внутри | От чего зависит |
|---|---|---|
| `actions/` | `RegimeTaskTree` — оркестратор очереди режимов, `RegimeLogger` — журнал прогонов в `data/regime_log.db` | всё остальное |
| `actions/recipes/` | Рецепты на Qt TaskTree: `VacuumTaskTree` и далее | **только `Qt::Core` + `Qt::TaskTree`** |
| `actions/workers/` | Воркеры и мониторы: `RegimeWorkers`, `ValveTestWorker`, `VacuumRunMonitor` | связывают рецепты с железом |
| `actions/legacy/` | Путь `QtConcurrent` + `QPromise`: `ActionHandler`, `InletAction`, `DataControlAction` | `ValveControl`, `DataAcquisition` напрямую |
| `actions/tests/` | `VacuumTreeTests` — тесты рецептов на моках | `Qt::Core`, `Qt::TaskTree`, gtest |

## Правило для `recipes/`

Файл из `recipes/` обязан собираться в `VacuumTreeTests` **без `ValveControl` и без
biodaq**. Это не организационное пожелание, а проверяемое условие: цель
`VacuumTreeTests` компилирует рецепты напрямую и линкуется только с
`Qt6::Core`, `Qt6::TaskTree` и `gtest`. Если рецепт начал требовать железо —
сборка тестов упадёт, и это правильный момент об этом узнать.

Всё, что рецепту нужно от внешнего мира, проходит через `std::function`-швы в
его контексте (`VacuumTreeContext` и аналоги). Швы, которые не обязательны,
объявляются nullable — тогда существующие тесты, их не задающие, продолжают
собираться.

Развязка не теоретическая: именно на моках нашлись обращение к
`Tasking::Storage` из таймера вне контекста дерева и «мёртвый датчик читается как
достигнутый вакуум».

## Правило для ожиданий

Ни `QThread::msleep`, ни `QEventLoop`, ни `QCoreApplication::processEvents()`
внутри обработчика задачи. Все выдержки — через `PauseBus` и `PausableTicker`:
иначе режим невозможно поставить на паузу, а вложенное исполнение обработчиков
роняло приложение при остановке (журнал дефектов, Day7).

## `legacy/`

`ActionHandler` вызывается из `Grams::testActionHandler()`, который сам ниоткуда
не вызывается: напуск через этот путь запускается только вручную из отладочного
кода. Файлы оставлены как справочник алгоритма при переносе напуска на рецепт —
удалять их до завершения переноса рано.

Новые режимы сюда **не добавляются**.

## Как добавить режим

1. Рецепт в `recipes/`: контекст со швами, узлы развёртки, `build<Имя>Recipe()`.
2. Воркер в `workers/`: наследует `RegimeWorkerBase` либо повторяет
   standalone-паттерн `VacuumRegimeWorker` (`start()` + `done(bool)`), заполняет
   контекст реальными указателями.
3. Монитор в `workers/`, если режиму нужна live-развёртка в UI.
4. Ветка по имени режима в `RegimeTaskTree::buildRegimeGroup()`.
5. Пункт в меню «Добавить» — `src/runtable/RunTable.qml`.
6. Тесты в `tests/` на моках швов.

CMake правок не требует: `src/CMakeLists.txt` собирает `*.h`/`*.cpp` из всех
четырёх папок через `file(GLOB …)`. Новая **подпапка** — потребует.
